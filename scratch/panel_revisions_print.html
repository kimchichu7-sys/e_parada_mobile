1. Chapter 1: Specific Objectives Revision (The Respondent Pivot) Chapter 1

The Problem: The paper previously stated that only IT developers would evaluate the system. The panel strictly corrected this: IT developers evaluate technical code and architectural quality, but actual stakeholders must evaluate the operational application.

"Ang IT developer, ite-test lang po niya is yung technical ng program... pero yung APPLICATION mismo, dapat USERS ang magte-test niyan! User acceptance / user evaluation!" — Thesis Panel

Required Textual Revision for Specific Objective 3:

  • Objective 3a (Technical Software Quality): To test and evaluate the technical software product quality of the E-Parada ecosystem through purposive testing by IT Developers and Software Engineering Professionals using the ISO/IEC 25010:2011 Software Product Quality Model in terms of Functional Suitability, Performance Efficiency, and Reliability.
  • Objective 3b (User Acceptance & Usability): To evaluate the user acceptance, usability, and operational suitability of the mobile applications and web portal among key stakeholders in Calamba City, Laguna—specifically Ten (10) Drivers/Motorists, Ten (10) Parking Space Providers, and Three (3) System Administrators—measuring Usability, User Error Protection, Learnability, and Operability.
2. Chapter 1: Scope & Limitations Alignment Chapter 1
  • Payment Processing Modality: Correct any ambiguity regarding cashless payments. State explicitly in Scope that E-Parada implements a dual-modality settlement framework: (1) Cashless payments via PayMongo API v1 integrating GCash with automated webhook verification, and (2) On-site Cash settlement with mutual confirmation handshakes. In Limitations, clarify that cashless payment is fully supported but dependent on third-party gateway uptime and active data connectivity.
  • Exclusion of E-Bikes and Bicycles: Explicitly delimit in Chapter 1 that the platform strictly caters to LTO-registered motor vehicles (Cars, Sedans, SUVs, Vans, Pickups, and Motorcycles). Bicycles, e-bikes, and light electric scooters are excluded due to the lack of government plate numbers, registration certificates (OR/CR), and licensing requirements.
  • Downpayment & No-Show Policy: Document the operational policy requiring an initial 1-hour downpayment upon reservation to protect parking owners from no-show cancellations.

PART 2: SYSTEM & SOFTWARE ENGINEERING REVISIONS
1. User Roles & Vehicle Ownership Differentiation Backend / Database

Problem Identified by Panel: The app assumed the driver is always the vehicle owner. What if someone drives a family car or company vehicle?

  • Registration Options: Allow users to register as:
    1. Driver Only: Submits a valid Driver's License.
    2. Vehicle Owner Only: Submits Government ID + OR/CR in their name.
    3. Owner & Driver (Both): Submits both Driver's License and OR/CR.
    4. Parking Space Provider: Routes to property onboarding.
2. Two-Factor Vehicle & Space KYC Verification Security & Verification
"Paano ive-verify kung hindi nakaw? Baka nakapark doon nakaw pala, demandahan pa yung may-ari nung parking!... Hindi pwedeng Valid ID lang sa provider, laging dalawa ang verification!" — Thesis Panel
  • Vehicle Registration KYC: Drivers must upload:
    1. Vehicle photo with visible license plate (for Tesseract OCR plate extraction).
    2. Official Certificate of Registration (CR) issued by the LTO.
    3. Current-year Official Receipt (OR) issued by the LTO.
    4. Valid Driver's License.
  • Parking Space Provider KYC: Providers must upload:
    1. Valid Government ID (with matching home address).
    2. Barangay Clearance / Certificate of Parking Operation issued by the local Calamba barangay explicitly authorizing parking operations at that specific address.
    3. (Optional upload slot): Real Property Tax Declaration or Land Title (TCT).
  • Admin Portal Review Interface: Provide side-by-side verification tabs allowing administrators to inspect the vehicle photo, OCR plate, OR/CR document, and license before issuing approval.
3. 1-Hour Downpayment & 1-Hour No-Show Cancellation Logic Reservation & Billing

Problem: Drivers who book a slot and never show up tie up the space and cause revenue loss for the provider.

  • Mandatory 1-Hour Downpayment: When reserving, the driver must immediately pay a downpayment equal to 1 hour of parking (e.g., ₱50 via GCash PayMongo).
  • Automated 60-Minute No-Show Cancellation: If the driver fails to arrive and scan the entry QR code within 60 minutes of the scheduled start time:
    • The reservation is automatically cancelled (Cancelled_NoShow).
    • The slot is immediately returned to the available inventory.
    • The 1-hour downpayment is forfeited by the driver and credited to the parking owner as compensation.
  • Remaining Balance Settlement: At exit, total duration is calculated: $ ext{Balance Due} = ext{Total Computed Bill} - ext{Downpayment Paid}$, payable via Cash or GCash.
4. Space Management: Batch Slot Configuration ("Select All") Provider Portal

Problem: Adding 15, 50, or 100 slots one by one is exhausting and impractical for providers.

  • Implement a "Select All" / Checkbox feature in the parking slot editor.
  • Allows providers to batch-assign vehicle types (e.g., set all to "Car/Sedan" or "SUV"), dimensions, and clearance with one click.
5. Communication Rules: Deactivate Chat on Inactive Bookings WebRTC & Chat
  • Hide and deactivate the in-app chat and WebRTC call buttons if the reservation is Cancelled, Rejected, or Completed. Communication is strictly reservation-bound.
6. Front-End Mobile & Web UI/UX Overhaul Mobile UI / UX

The panel strongly criticized the visual clutter, tiny text, and monochromatic color scheme in the demo:

UI / UX Dimension Panel Observation Required Technical Implementation
Functional Color-Coding "Puro blue, ang dumi tingnan... walang distinction." • Green buttons: Approve, Confirm, Pay Now.
• Red buttons: Cancel, Reject, Delete, Overstay alert.
• Neutral slate/white: Card containers and headers.
Typography & Readability "Napakaliit ng text... paano kung matanda ang driver o owner? Hahabulin ng magnifying glass?" • Enlarge base body text from 11sp to 14sp–16sp.
• Headers set to 18sp–22sp Bold.
• Minimum touch target height of 48dp on all buttons.
Screen Clutter & Architecture "Ang gulo... ang daming nakasulat na hindi maintindihan kung ano ang pipindutin." • Separate History Tab: Move past/cancelled bookings to a dedicated History screen.
• Main screen displays ONLY the currently active reservation card.
Card Presentation Raw text dumped across the entire screen. • Cascading / Collapsible Cards: Clean summary cards that smoothly expand when clicked to reveal details and 2D floor plans.
